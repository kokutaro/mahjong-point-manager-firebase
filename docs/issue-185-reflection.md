## 3. 学び

- 確認画面を挟む処理では、表示時点と確定時点の間にデータが変わることを前提に設計する必要がある。
- 複数ドキュメントの状態が同時に正しくなければならない操作は、クライアントの購読スナップショットだけで検証せず、トランザクション内で最新状態を検証する。
- 要件に複数の評価指標が列挙されている場合、明示されていない独自の優先条件を先頭に追加しない。境界条件は指標の既定値として表現する。
- 「人が最終判断する」UIでは変更差分だけでなく、変更後の全体像を提示する。

## 4. 改善アクション

1. 提案→確認→確定の機能では、確定直前の再計算とサーバー側競合検証を設計チェックリストへ追加する。
2. ソート要件は比較キーを優先順にテスト名と仕様書へ明記する。
3. 既存データ互換用のoptional型と、新規作成時の必須入力型を分離する。
4. 非同期確認UIでは成功可否を明示的に返し、失敗時に閉じないテストを追加する。

## 5. 検証方針

- 累計点数・平均順位・未対局・同点・ユーザーID解決・卓ランク・混在卓・既存配置・空席不足を純粋関数テストで確認する。
- 卓の同時変更と参加者の非`idle`化をトランザクションのサービステストで確認する。
- 最終卓構成の表示、明示確認、キャンセル、反映失敗時に閉じない動作をコンポーネントテストで確認する。
- 全体のlint、build、unit/component/service tests、coverageを最終確認する。
